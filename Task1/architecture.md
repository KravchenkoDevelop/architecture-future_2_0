# Задание 1. Проектирование целевой архитектуры «Будущее 2.0»

---

## 1. Целевая архитектура — диаграмма контейнеров (C4 Level 2)

### Архитектурная концепция: Data Mesh + Cloud-Native

Целевая архитектура строится на принципах **Data Mesh**: каждый бизнес-домен владеет своими данными и публикует их как «продукт данных» (Data Product) для аналитической платформы. Монолитный DWH на SQL Server 2008 заменяется облачным **Data Lakehouse** с разделением по доменам. ESB заменяется брокером событий (Kafka).



### Ключевые архитектурные решения и их связь с бизнес-сценариями

| Решение | Обоснование | Поддерживаемые сценарии |
|---|---|---|
| Data Lakehouse (Cloud) вместо DWH SQL Server 2008 | EoL-версия СУБД, недопустимая производительность, нет масштабирования | Быстрая отчётность, масштабирование |
| Data Mesh: каждый домен — владелец Data Product | Убирает bottleneck DWH, даёт доменам независимость | Независимое развитие финтех и ИИ, подключение фармы |
| Портал самообслуживания | Бизнес-пользователи сами строят отчёты без запросов в IT | Быстрая отчётность, управленческие решения |
| Kafka вместо ESB (Apache Camel) | Слабая связность, масштабируемость, event-driven интеграция | Независимое развитие, интеграция новых бизнесов |
| Изоляция EMR (медкарты не в аналитике) | Регуляторные требования (152-ФЗ, HIPAA), конфиденциальность | Качество медицинских сервисов, compliance |
| API Gateway + IAM | Единая точка безопасного подключения партнёров | Масштабирование, подключение фармы и medEquip |
| Отдельный домен для ИИ (собственное хранилище) | ИИ-команда деплоит независимо, не ждёт DWH | Качество ИИ-диагностики, time-to-market |
| Замена PowerBuilder на Web App | Устаревший стек, нет мобильности, невозможно масштабировать | Операционная эффективность клиник |

## 2. Декомпозиция ESB-монолита (Apache Camel)

> **Важное уточнение.** В текущей архитектуре ESB выполняет не только роль транспорта — это монолит логики с тремя принципиально разными функциями. Заменить его «просто Kafka» нельзя: необходимо явно распределить каждую функцию по новым ответственным компонентам.

### 2.1 Что сейчас делает ESB

| Функция ESB | Описание | Проблема |
|---|---|---|
| **Транспорт / интеграции** | Маршрутизация сообщений между системами (DWH, клиники, финтех, внешние) | SPOF, нет гарантий доставки, нет масштабирования |
| **ФЛК (форматно-логический контроль)** | Валидация форматов, обязательных полей, бизнес-правил входящих данных (мед. документы, финансовые транзакции) | Логика вшита в Camel-роуты: невидима, нетестируема, нет версионирования |
| **Трансформации данных** | Маппинг форматов (HL7 → внутренний формат, XML ↔ JSON), агрегации, конвертации справочников | Трансформации неотделимы от маршрутизации: любое изменение = риск регрессии во всей шине |
| **Оркестрация процессов** | Реализация части бизнес-процессов через цепочки Camel-роутов | *Out of scope для текущей итерации* |

### 2.2 Целевое распределение функций ESB

```
БЫЛО (Apache Camel ESB — монолит):
  Транспорт + ФЛК + Трансформации + Процессы → один Camel-контекст

СТАЛО (декомпозиция):
  ┌─────────────────────────────────────────────────────────┐
  │ Функция ESB        → Целевой компонент                  │
  ├─────────────────────────────────────────────────────────┤
  │ Транспорт          → Apache Kafka                       │
  │ ФЛК                → Domain Validation Service (каждый │
  │                       домен валидирует свои данные)     │
  │ Трансформации      → dbt (аналитика) + Adapter/Anti-   │
  │                       Corruption Layer в каждом сервисе │
  │ Процессы           → BPMS / out of scope               │
  └─────────────────────────────────────────────────────────┘
```

### 2.3 Как уходим от монолита с логикой — детально

#### Транспорт → Apache Kafka

Kafka заменяет только **транспортную** функцию ESB: надёжная асинхронная доставка событий между доменами. Каждый домен публикует события в собственный топик (`fintech.transactions`, `clinics.appointments`). Консьюмеры читают независимо. Отказ одного консьюмера не влияет на других.

#### ФЛК → Domain Validation Services (принцип «домен владеет своей логикой»)

Бизнес-правила валидации **переносятся в сервис того домена, которому принадлежат данные**:

| Домен | Что валидировалось в ESB | Кто валидирует в целевой архитектуре |
|---|---|---|
| Клиники / EMR | Формат HL7 FHIR, обязательные поля медкарты, коды диагнозов МКБ-10 | EMR Validation Service (при приёме данных в EMR-домен) |
| Финтех | Форматы транзакций, суммы, BBAN/IBAN, лимиты | Fintech Domain Service (при входящем событии) |
| ИИ-диагностика | Полнота и формат входных признаков модели | AI Platform (Data Contract на входе пайплайна) |
| HQ / Аналитика | Корректность справочников, дата-контракты Data Product | Data Product Layer (Schema Registry + Great Expectations) |

Ключевой принцип: **ФЛК — это часть бизнес-логики домена, а не инфраструктурная функция шины**. В текущем ESB она накоплена в одном месте — это делает её невидимой и нетестируемой. В целевой архитектуре каждый домен декларирует правила валидации явно (Schema Registry, контракты, тесты).

#### Трансформации → dbt + Anti-Corruption Layer

Трансформации разделяются по назначению:

- **Аналитические трансформации** (агрегации, метрики, исторические срезы) → **dbt** в слое Data Lakehouse. Декларативный SQL, версионирование, тесты, lineage.
- **Структурные трансформации при интеграции** (маппинг форматов между системами: HL7↔JSON, SOAP↔REST) → **Anti-Corruption Layer** на стороне домена-получателя. Каждый домен адаптирует чужой формат на своей границе, не полагаясь на центральную шину.
- **Справочники и конвертации** → выделяются в отдельный **Reference Data Service** (читается всеми доменами, но не зависит от ESB).

#### Итог: что меняется архитектурно

| Характеристика | ESB (было) | Целевая архитектура (стало) |
|---|---|---|
| Где живёт бизнес-логика | В центральных Camel-роутах | В каждом домене, декларативно |
| Видимость правил ФЛК | Скрыта в XML/Java-роутах | Явные схемы (Schema Registry), тесты (Great Expectations) |
| Тестирование трансформаций | Нет (интеграционные тесты всей шины) | Unit-тесты dbt, контрактные тесты ACL |
| Отказоустойчивость | SPOF — падение ESB = остановка всего | Изолированные отказы по доменам |
| Масштабирование | Вертикальное (один Camel-кластер) | Горизонтальное (Kafka partitions, независимые consumer groups) |
| Версионирование логики | Нет | Schema Registry, Git-история dbt-моделей |

## 4. Проблемные места текущей архитектуры

### Таблица проблем

| # | Проблема | Описание | Страдающие бизнес-сценарии | Риск |
|---|---|---|---|---|
| P1 | **DWH на SQL Server 2008 — узкое горлышко** | EoL-система (поддержка закончилась в 2019). Сотни терабайт данных, сложные трансформации. Отчёты строятся часами. Вся бизнес-логика вшита в DWH, изменения одного домена ломают других | Быстрая отчётность, управленческие решения, все интеграции | Критический |
| P2 | **Отсутствие изоляции доменов** | Финтех, ИИ, медицина и HQ делят один DWH. Релиз финтеха требует координации с медицинской командой. Деградация производительности влияет на всех | Независимое развитие финтех и ИИ, time-to-market | Высокий |
| P3 | **PowerBuilder — устаревший клиентский интерфейс** | Технология 1990-х годов. Нет мобильной версии, крайне сложно нанимать разработчиков, невозможна интеграция с современными ИИ-сервисами. Дорогостоящая поддержка | Операционная работа врачей и операторов, ИИ-диагностика | Высокий |
| P4 | **ESB (Apache Camel) — единая точка отказа** | Все потоки данных (ИИ, финтех, внутренние сервисы) идут через одну шину. Нет изоляции отказов: падение ESB останавливает работу всех сервисов. Нет гарантий доставки | Независимое развитие, интеграция новых бизнесов, операционная непрерывность | Высокий |
| P5 | **Нет портала самообслуживания** | Аналитики и менеджеры полностью зависят от IT для получения любого нового среза данных. Очередь запросов, задержки решений. Power BI с кастомизациями не покрывает потребность в ad-hoc анализе | Быстрая отчётность, управленческие решения | Высокий |
| P6 | **On-premise инфраструктура — нет масштабирования** | Фиксированные ресурсы серверов нельзя нарастить под пиковую нагрузку. Подключение нового бизнес-направления требует закупки оборудования и месяцев конфигурации. Высокие CAPEX | Масштабирование для новых бизнесов (фарма, medEquip), time-to-market | Высокий |
| P7 | **Отсутствие Data Governance и каталога данных** | Нет единого реестра метаданных, нет lineage, нет контроля качества данных. Невозможно проследить происхождение числа в отчёте. Сложно соблюдать регуляторные требования по работе с ПД | Регуляторное соответствие (152-ФЗ, банковские нормативы), доверие к отчётам | Средний |
| P8 | **Бизнес-логика сосредоточена в DWH** | Правила расчёта финансовых показателей, медицинских метрик и HR-данных перемешаны в хранимых процедурах SQL Server. Любое изменение — риск регрессий. Тестирование крайне затруднено | Скорость разработки всех направлений, надёжность отчётности | Средний |
| P9 | **Медицинские данные в общем DWH без изоляции** | Карты пациентов хранятся вместе с финансовыми данными. Нет гарантированной изоляции доступа на уровне архитектуры, только на уровне прав. Риск утечки при SQL-инъекции или ошибке разработчика | Соответствие 152-ФЗ и медицинской тайне, репутация | Критический |
| P10 | **Нет механизма подключения внешних партнёров** | Для интеграции фармацевтических компаний и производителя медоборудования нет готовой точки входа. Каждая интеграция — отдельная разработка «в обход» архитектуры | Масштабирование экосистемы, выручка от партнёрств | Средний |

## 5. Приоритизация проблем

### 5.1 Матрица Эйзенхауэра

```
                    СРОЧНО                          НЕ СРОЧНО
          ┌──────────────────────────┬──────────────────────────┐
          │  СДЕЛАТЬ НЕМЕДЛЕННО      │  ЗАПЛАНИРОВАТЬ           │
ВАЖНО     │                          │                          │
          │  P1 — DWH-бутылочное    │  P2 — Изоляция доменов   │
          │       горлышко           │  P5 — Портал             │
          │  P9 — Изоляция          │       самообслуживания    │
          │       медданных          │  P6 — Cloud-миграция     │
          │  P4 — ESB SPOF          │  P7 — Data Governance    │
          ├──────────────────────────┼──────────────────────────┤
          │  ДЕЛЕГИРОВАТЬ /          │  ДЕЛАТЬ ПОСЛЕДНИМ /      │
НЕ ВАЖНО  │  ПАРАЛЛЕЛЬНО             │  НЕ ДЕЛАТЬ               │
          │                          │                          │
          │  P3 — PowerBuilder →    │  P10 — Partner API GW    │
          │       Web App            │        (после cloud)     │
          │  P8 — Бизнес-логика     │                          │
          │       из DWH             │                          │
          └──────────────────────────┴──────────────────────────┘
```

**Обоснование срочности:**
- P1, P9 — текущий ущерб бизнесу происходит прямо сейчас (часовые отчёты, юридический риск).
- P4 — ESB как SPOF создаёт риск полного останова операций.
- P2, P5, P6 — критически важны для достижения целей через год, но требуют планирования.
- P3, P8 — важны, но не блокируют стратегические цели в краткосрочной перспективе.

### 5.2 Приоритизация по MoSCoW

#### MUST HAVE — без этого целевая архитектура недостижима

| Проблема | Решение | Связь с бизнес-целями |
|---|---|---|
| **P1** — DWH SQL Server 2008 | Миграция на Cloud Data Lakehouse (Azure Synapse / AWS Redshift + Delta Lake) | **Выручка**: задержки отчётов → задержки управленческих решений → упущенная выгода. **Безопасность**: EoL-система без патчей безопасности |
| **P9** — Медданные без изоляции | Выделить EMR как отдельный FHIR-сервис с изолированным хранилищем, убрать медкарты из общего DWH | **Compliance**: нарушение 152-ФЗ и медицинской тайны — угроза лицензии клиник. **Репутация** |
| **P5** — Нет портала самообслуживания | Реализовать Self-Service Data Portal (Superset / Cube.js) поверх Lakehouse | **Выручка**: прямое требование руководства. **Скорость решений**: менеджеры не ждут IT |
| **P2** — Нет изоляции доменов | Определить границы доменов, ввести Data Product-подход | **Time-to-market**: финтех и ИИ релизят независимо, не ждут общий DWH |

#### SHOULD HAVE — необходимо для устойчивости архитектуры

| Проблема | Решение | Связь с бизнес-целями |
|---|---|---|
| **P4** — ESB как SPOF | Декомпозиция Apache Camel ESB: транспорт → Kafka, ФЛК → domain-сервисы, трансформации → dbt/сервисы | **Операционная непрерывность**: отказ шины = остановка всего. **Масштабирование**: Kafka масштабируется горизонтально |
| **P6** — On-premise, нет масштабирования | Cloud-миграция (IaaS → PaaS), отдельные cloud-окружения по доменам | **Масштабирование**: подключение фармы/medEquip без закупки железа. **OPEX**: снижение затрат на инфраструктуру |
| **P7** — Нет Data Governance | Data Catalog (Apache Atlas), RBAC через IAM, Data Lineage | **Compliance**: банковские нормативы ЦБ, 152-ФЗ. **Доверие к данным**: отчётам можно верить |

#### COULD HAVE — желательно, но не блокирует достижение целей через год

| Проблема | Решение | Связь с бизнес-целями |
|---|---|---|
| **P3** — PowerBuilder | Постепенная замена на Web App (React / PWA) | **Качество сервисов**: UX врачей, мобильный доступ. **Найм**: разработчики PowerBuilder = редкость |
| **P8** — Бизнес-логика в DWH | Перенос трансформаций в dbt, логики — в сервисы доменов | **Скорость разработки**: снижение риска регрессий, тестируемость |

#### WON'T HAVE (в горизонте года, но в roadmap)

| Проблема | Обоснование | Когда |
|---|---|---|
| **P10** — Partner API Gateway для фармы | Требует готовой cloud-инфраструктуры и стабильных доменов. Нельзя строить интеграцию на нестабильном основании | Год 2, после cloud-миграции |
| Полная замена всех legacy-систем | Бизнес допускает временное сохранение legacy в отдельных доменах | Поэтапно, по мере готовности доменных команд |

### 5.3 Итоговый приоритетный порядок реализации

```
Квартал 1 (сейчас → 3 мес.)
├── [MUST] Определить границы доменов, сформировать Data Product-контракты
├── [MUST] Начать cloud-миграцию: поднять Data Lakehouse (MVP)
└── [MUST] Изолировать медицинские данные (EMR → отдельный сервис)

Квартал 2 (3 → 6 мес.)
├── [MUST] Запустить первые Data Products: Финтех + Клиники → Lakehouse
├── [MUST] MVP Портала самообслуживания (базовый ad-hoc анализ)
└── [SHOULD] Начать декомпозицию ESB: запустить Kafka, вынести ФЛК одного домена (пилот)

Квартал 3 (6 → 9 мес.)
├── [SHOULD] Полная декомпозиция ESB: ФЛК → domain-сервисы, трансформации → dbt/ACL, вывод ESB
├── [SHOULD] Data Governance: каталог, RBAC, lineage
└── [COULD] Начать замену PowerBuilder (пилот)

Квартал 4 (9 → 12 мес.)
├── [MUST] Полнофункциональный Портал самообслуживания
├── [COULD] PowerBuilder → Web App (полный переход)
└── [COULD] Перенос бизнес-логики из DWH в domain-сервисы
```

### Связь приоритетов с бизнес-целями

| Бизнес-цель | Критичные проблемы | MoSCoW-приоритет |
|---|---|---|
| Выручка (финтех + клиники) | P1 (медленные решения), P2 (медленный time-to-market финтеха), P9 (риск лицензии) | Must |
| Time-to-market (ИИ и финтех) | P2 (нет изоляции), P4 (ESB-зависимость), P8 (логика в DWH) | Must / Should |
| Качество медицинских сервисов | P3 (PowerBuilder), P9 (изоляция медданных), ИИ-интеграция | Must / Could |
| Качество финансовых сервисов | P1 (данные для решений), P7 (governance для ЦБ), P4 (надёжность) | Must / Should |
| Масштабирование (фарма, medEquip) | P6 (нет cloud), P10 (нет Partner API), P4 (ESB не масштабируется) | Should / Won't (now) |
| Управленческая отчётность | P1 (скорость), P5 (self-service), P7 (доверие к данным) | Must |
